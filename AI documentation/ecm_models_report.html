Короткий висновок

ECM не є mesh-форматом

ECM є високорівневим описом персонажа/об'єкта: він посилається на .smd skin model, actions, GFX, Lua scripts, child ECM, додаткові skins, hooks, shader settings і фізику.

Колізія має два шари

Перший шар: convex hull дані з окремого .ecp у grasses\ECModelHull. Другий шар: PhysX rigid-body/skeleton sync data, файл вказується рядком PhysFileName у ECM.

Поточна ECM-версія: 67

Код завантажує ECM тільки якщо версія не більша за EC_MODEL_CUR_VERSION = 67. Поточна збірка записує ECM як text-файл, бо MODEL_FILE_TYPE визначено як AFILE_TEXT.

Важливе уточнення: у коді є binary-гілки file.IsBinary(), але у цьому checkout MODEL_FILE_TYPE дорівнює AFILE_TEXT. Тобто нормальний CECModelStaticData::Save створює текстовий ECM, а binary-гілка виглядає як спадщина/альтернативна конфігурація.

Що таке ECM модель

CECModel складається з двох рівнів:

РівеньКласРоль
Static/shared data CECModelStaticData Завантажується через AfxGetECModelMan()->LoadModelData(), кешується менеджером, містить усі дані з ECM-файлу: шлях до SMD, actions, scripts, child info, hull, phys sync data, hooks, shaders.
Runtime instance CECModel Живий екземпляр у сцені: має позицію/напрям/scale через A3DCoordinate, власний A3DSkinModel, runtime GFX копії, child model instances, physics object, play speed, visibility, AABB.

Внутрішні компоненти ECM

За полями CECModelStaticData ECM містить або може містити:

  • SkinModelPath: шлях до .smd, тобто реальної skinned mesh-моделі.
  • AdditionalSkin: список додаткових skin-файлів для редактора/кастомізації.
  • A3DCombinedAction: складені дії, events, GFX/SFX/trails/camera/audio/model-scale events.
  • CoGfxMap: GFX, які постійно прив'язані до моделі.
  • Scripts: Lua-like script blocks для старту/зупинки action, init/release, model loaded, change equip, phys break.
  • ChildInfoArray: дочірні ECM-моделі, які вішаються на hook/bone.
  • ConvexHullDataArray: hull-колізії, завантажені не з самого ECM, а із зовнішнього .ecp.
  • PhysFileName + A3DModelPhysSyncData: фізика skeleton rigid body.
  • ECModelHookMap: custom ECM hooks, окремо від skeleton hooks.
  • PixelShader, ShaderTex, PSConsts: заміна/анімація shader constants.
  • BoneScale/BoneScaleEx, action channels, event masks, blend/shadow/render flags.

Ментальна модель

ECM file
  -> CECModelStaticData
      -> SMD path -> A3DSkinModel
      -> Combined actions/events/scripts
      -> CoGfx list and child ECM list
      -> PhysFileName -> A3DModelPhysSyncData
      -> external .ecp hulls -> CConvexHullData[]
  -> CECModel runtime instance
      -> Tick: actions, skin/physics, events, GFX, children
      -> Render: skin model, action FX, CoGfx, child ECM
      -> Collision users read GetConvexHullData() or enable PhysX

Binary-гілка

У LoadData/Save є гілки для file.IsBinary(): версія як DWORD, ReadString/WriteString, raw arrays. Але MODEL_FILE_TYPE зараз AFILE_TEXT, тому стандартний writer не пише binary ECM. Якщо зустрінеться binary ECM з іншої збірки, треба перевіряти конфігурацію рушія/макроси.

Як ECM працює в runtime

Load pipeline

  1. CECModel::Load() бере static data через AfxGetECModelMan()->LoadModelData(szModelFile).
  2. Копіює event masks і створює runtime-копії CoGfx, завантажуючи відповідні A3DGFXEx.
  3. Завантажує A3DSkinModel зі SkinModelPath. Якщо шлях - лише filename, пробує знайти поруч із ECM.
  4. Вимикає auto-update child у A3DSkinModel, бо child ECM оновлюються власною логікою CECModel.
  5. Застосовує shader/material defaults, bone scale, additional skins у editor mode.
  6. Якщо bLoadChildECModel, викликає LoadChildModels() і створює child instances.
  7. Викликає script event ModelLoaded.
  8. Будує action channels на skeleton joints.
  9. Якщо bIsCreateModelPhys і фізика ввімкнена, створює A3DModelPhysics.

Tick pipeline

CECModel::Tick(dwDeltaTime, bNoAnim) масштабує час через play speed/delay mode і далі оновлює:

  • channel combined actions;
  • skin model або physics-driven skin через TickSkinModel;
  • motion blur;
  • combined action events;
  • fade-out SFX;
  • CoGfx;
  • shown child models;
  • після всього оновлює загальний AABB.

Render pipeline

Render() спершу оновлює lighting для skin model, рендерить action FX, перевіряє visibility через AABB, малює SMD, додає shadow caster, реєструє motion blur, рендерить CoGfx і рекурсивно child ECM.

Якщо у ECM є convex hull AABB, render visibility бере GetCHAABB(), трансформує center, робить extents сферичними через max(x,y,z), і merge-ить із m_ModelAABB. Коментар у коді каже, що для часткових hulls одного CH AABB недостатньо, тому merge важливий.

Як підключаються колізії ECM

У ECM є окрема система convex hull колізій. Вона не лежить безпосередньо у текстовому ECM-файлі. Loader після читання ECM шукає зовнішній .ecp файл у спеціальній папці.

Де шукається .ecp

const char* AfxGetECMHullPath() -> "grasses\\ECModelHull"

szModelFile = "Models\\Npcs\\foo\\foo.ecm"
szPath = first substring from first "\\"
szProjFile = AfxGetECMHullPath() + szPath
extension changed to ".ecp"

Тобто логіка приблизно така: ECM ...\foo.ecm має відповідний hull-проєкт grasses\ECModelHull\...\foo.ecp. Якщо файла нема, це не помилка: ECM просто не матиме CHAABB/hulls.

Старий .ecp header, який реально читає CECModelStaticData

struct ECModelBrushProjHead_t {
  unsigned int nMagic;      // ('e'<<24)|('c'<<16)|('b'<<8)|('p')
  unsigned int nVersion;    // 0x00000001
  char szECModelFile[MAX_PATH];
  int nFrame;
  unsigned int nNumHull;
};

for each hull:
  CConvexHullData::LoadBinaryData(file)

Після читання кожен hull додатково трансформується матрицею TransformMatrix(dir=(0,0,-1), up=(0,1,0), pos=0). Коментар у коді пояснює це як компенсацію помилки редактора hull-ів, який повертав модель на 180 градусів.

Новий ConvexHullArchive формат

Клас ConvexHullArchive підтримує новий header v2, хоча ECM loader у CECModelStaticData напряму читає старий ECModelBrushProjHead_t. Новий archive layout:

int fileId = 0xffffffff
int version = 2
int genType = 1(MOX) або 2(ECM)
char modelFile[MAX_PATH]
if genType == ECM:
  int frame
int nNumHull
hull 1..n

Також є fallback для старого .chf MOX collision-файлу: якщо перший int не fileId і не ecbp magic, loader трактує це як старий .chf, читає hull count і пропускає mesh id таблицю.

  • CECModel сам дає доступ через HasCHAABB(), GetCHAABB(), GetConvexHullData().

PhysX-фізика ECM

PhysX не є тим самим, що .ecp convex hull. Це окремий механізм rigid body / skeleton synchronization. Він працює тільки під #ifdef A3D_PHYSX.

Як ECM підключає PhysX

  1. У ECM V34+ є рядок PhysFileName: fileName.
  2. CECModelStaticData::LoadData будує шлях поруч із ECM: бере szModelFile і замінює filename на m_strPhysFileName.
  3. Якщо файл існує, створюється A3DModelPhysSyncData і викликається Load().
  4. CECModel::EnablePhysSystem() ставить m_bPhysEnabled = true і викликає CreateModelPhysics().
  5. CreateModelPhysics() створює A3DModelPhysics, викликає Init(gGetAPhysXScene(), this), потім CreateModelSync(m_pMapModel->m_pPhysSyncData).
  6. A3DModelPhysics::CreateModelSync викликає A3DModelPhysSyncData::InitBind(m_pSkinModel), створює A3DModelPhysSync, bind-ить skeleton rigid body object до skin model.

Child physical links

Child ECM має два рівні прив'язки:

  • Візуальна прив'язка: AddChildModel(hangerName, bOnBone, hookName, child, ccName), де child висить на parent hook/bone.
  • Фізична прив'язка: OpenChildModelLink/AddChildModelLink з parentHook і childAttacher. Вона працює через A3DModelPhysSync::OpenPhysLinkAsChildModel і APhysXRBAttacher.

При recursive EnablePhysSystem(..., bRecur=true) ECM намагається відновити збережені m_PhysHookAttachLinks для child models.

Обмеження та ризики сумісності

  • Версія ECM: loader відмовляється від Version > 67.
  • V1/V4: в історії коду не описані. Не варто робити припущення про їх layout без реальних файлів.
  • Text vs binary: поточний writer пише text ECM; binary гілка є, але не є типовою для цього build.
  • SMD path V37/V38: коментар прямо каже, що у V37 були файли, де збережено лише filename, і це виявилось несумісним з проєктом; V38 повернув relative pathname.
  • Hull файл optional: відсутній .ecp не валить load. Просто не буде HasCHAABB().
  • Hull coordinate fix: loader повертає hull назад через 180-degree correction. Якщо генерувати .ecp вручну, треба врахувати цю компенсацію.
  • Hull flags: collision/raytrace можуть пропускати hull, якщо стоять CHDATA_SKIP_COLLISION або CHDATA_SKIP_RAYTRACE.
  • PhysX optional: уся PhysX логіка залежить від A3D_PHYSX, наявності gGetAPhysXScene(), валідного A3DModelPhysSyncData і SMD skeleton.
  • PhysSyncData прив'язана до skeleton: actor/joint/bone/attacher names мають збігатися з bones/hooks SMD, інакше InitBind повертає помилки типу no root bone, no bone, actor not linked, attacher hook not exist.
  • Child physical links: візуальний child link не гарантує фізичний link; потрібні attachers і виклик OpenChildModelLink/AddChildModelLink.
  • Scripts: з V26 scripts кодуються Base64 рядками. Пошкоджений Base64 або неправильний script id може зламати behavior, навіть якщо модель рендериться.

Практичні висновки для інструментів/конвертерів

Якщо задача - зробити exporter ECM з Blender, не треба писати mesh напряму в ECM. Правильна схема: експортувати/мати .smd skin model, а ECM генерувати як descriptor, який посилається на SMD і додаткові ресурси.
  1. Для мінімального ECM потрібні: Version, SkinModelPath, базові material/render fields, ComActCount: 0, ScriptCount: 0, AddiSkinCount: 0, ChildCount: 0, пустий PhysFileName, ECMHookCount: 0. Але точний мінімум треба перевіряти на реальному loader/editor build.
  2. Для picking/collision без PhysX треба окремо створювати .ecp у mirror path під grasses\ECModelHull.
  3. Для фізики треба генерувати не .ecp, а PhysSyncData v10 файл з actors/joints/attachers, і записати його ім'я в PhysFileName.
  4. Якщо модель має child ECM, у ECM записуються ChildName, ChildPath, HHName, CCName. Для фізичної child-прив'язки потрібні ще attachers у PhysSyncData.
  5. Якщо треба сумісність з клієнтом, не створювати ECM з версією вище 67 і не покладатися на undocumented V1/V4.
  6. Для static world/building collision краще не плутати ECM hull з BMD/MOX brush collision: ECM hull - dynamic model/person/object hull; BMD/MOX world collision у коді йде через інші класи building/brush.

Найкорисніша схема підключення колізій

ECM visual:
  .ecm -> SkinModelPath -> .smd -> A3DSkinModel

Picking / gameplay hull:
  .ecm path -> grasses\\ECModelHull\\same-relative-path.ecp
  .ecp -> CConvexHullData[] -> HasCHAABB/GetConvexHullData
  users -> RayIntersectWithCH / SphereCollideWithCH / CCDBrush

PhysX:
  .ecm -> PhysFileName -> A3DModelPhysSyncData v10
  A3DModelPhysics + A3DModelPhysSync
  actors/joints/attachers -> PhysX skeleton rigid body
  collision channels -> independent/common/parent/majorRB

Короткий чеклист перевірки ECM-файлу

  • Version не більша за 67.
  • SkinModelPath існує або файл лежить поруч із ECM, якщо path тільки filename.
  • Якщо є PhysFileName, файл існує поруч із ECM і відповідає skeleton bones/hooks.
  • Якщо потрібна hull collision, існує відповідний .ecp у grasses\ECModelHull.
  • Якщо hull створено зовнішнім інструментом, перевірити 180-degree correction loader-а.
  • Child ECM paths існують, а HHName/CCName мають сенс для parent/child skeleton hooks.
  • Scripts Base64 decode коректний, script ids у діапазоні 0..enumECMScriptCount-1.
  • CoGfx/GFX paths існують і не залежать від editor-only resources.

Підсумок

ECM у цьому рушії - це “розумна модель”, а не геометрія. Геометрія приходить із SMD, effects/actions/scripts живуть у ECM, picking/gameplay collision зазвичай приходить із external ECP convex hull, а фізика - з окремого PhysSyncData файлу. Для будь-якого exporter-а або редактора головне не змішувати ці три шари: visual SMD, hull ECP, PhysX sync data.
